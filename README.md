# cargo-grime-cremator

> *cremate the grime in your cargo target dir without burning down the cache*

A garbage collector for cargo target directories. Installs as the `cargo-gc`
binary so it can be invoked as a cargo subcommand:

```
cargo gc
```

Identifies and removes stale `deps/`, `build/`, `incremental/`, and top-level
artifacts that are no longer referenced by the project's current `Cargo.lock`
— **without invoking `rustc` or `cargo build`**. Safe to run repeatedly: a
fresh build followed by `cargo gc` is a fixed point. Running it again does
nothing. Building again does nothing.

## Why

A bevy/rapier app with ~500 transitive deps will balloon a `target/` dir from
12 GB to 60+ GB after a few `Cargo.lock` changes, because cargo never garbage
collects per-project. The traditional answer is `rm -rf target` — but that
costs an hour of recompilation. The other tools in this space
([cargo-sweep][], [cargo-clean-all][], [cargo-prune][]) all rely on
mtime/timestamp heuristics that either over-delete (causing recompiles) or
under-delete (leaving the dumpster full). Upstream cargo's per-project GC
([rust-lang/cargo#13136][upstream]) is still WIP.

`cargo-gc` uses a precise approach: it cross-references the on-disk
fingerprint metadata cargo writes against the current dependency graph, and
removes only what cargo can no longer reach.

## Use cases

These are the situations the tool is built for. If you recognize one,
this is probably the tool you want.

1. **"My target dir is X GB and growing and I'm out of disk."** The
   default `cargo gc` reclaims rustc incremental sessions, fingerprints
   for crates that have been removed from `Cargo.lock`, and per-unit
   configurations that haven't been touched in over a month. Pair it
   with a fresh `cargo build` and you'll never have to `rm -rf target`
   again.

2. **"I need an `rm -rf target` *right now* but without losing the build
   I just did."** `cargo build && cargo gc --max-age '1 hour'`. The
   build refreshes everything you actually use; the GC sweeps everything
   else. On a 53 GB bevy/rapier target dir this reclaims ~50 GB and the
   next build is still a no-op.

3. **"I've been switching feature flags / profiles / cfg combos and
   the orphans are piling up."** Each unique `(crate, features, profile,
   target-triple, rustc-version)` combo cargo has ever built leaves a
   distinct fingerprint dir behind, and cargo never reclaims them. The
   per-unit age sweep catches these once they're a month old. To catch
   them sooner, tighten `--max-age`.

4. **"I removed `model-viewer` from `Cargo.toml` weeks ago and its
   artifacts are still hogging 1.5 GB."** The crate-name sweep (always
   on, no flag needed) removes any fingerprint whose crate is gone from
   the current `cargo metadata` graph. It runs on the first invocation.

5. **"I'm done with the release profile for now."**
   `cargo gc --prune-profile release` wipes `target/release/` entirely.
   `--prune-profile` is repeatable and accepts custom profile names too.

6. **"I'm not going to touch one specific bin for a while, drop its
   artifacts but keep the shared dep tree."** `cargo gc --prune-target
   <binname>`. Wipes the bin's own fingerprint, deps, build, and
   incremental entries across every profile dir. Shared deps stay intact,
   so the next build of *other* targets is still a no-op and the next
   build of that bin itself just relinks instead of recompiling its
   transitive dep tree.

7. **"Cron job: build, gc, sleep, repeat."** The default loop
   `(cargo build; cargo gc)` is a fixed point on iteration two — both
   commands become no-ops once the dumpster is clean. You can run it as
   a post-build hook with no risk of extending build times.

8. **"What can I prune?"** `cargo gc --list` enumerates the workspace
   targets and on-disk profile dirs available to `--prune-target` and
   `--prune-profile`. No surprises, no need to remember exact names.

## Install

```sh
cargo install --path .
```

The binary is named `cargo-gc`, so `cargo gc` will work as a subcommand
once it's on your `PATH`.

## Usage

```
cargo gc                                # clean the current project (auto-detect target dir)
cargo gc --dry-run                      # show what would be removed
cargo gc -v                             # verbose: print every removal
cargo gc --target-dir /elsewhere        # explicit target dir override
cargo gc --manifest-path foo/Cargo.toml
cargo gc --profile release              # only sweep one profile dir (default: all of them)
cargo gc --keep-sessions 2              # keep N most recent rustc incremental sessions per crate
cargo gc --max-age '4 days'             # per-unit age cutoff (default "1 month", "never" disables)
cargo gc --max-age '2025-02-21 13:00:00'   # absolute UTC cutoff
cargo gc --prune-profile release        # nuke target/release/ entirely
cargo gc --prune-target model-viewer    # nuke that workspace target's artifacts in every profile
cargo gc --list                         # list workspace targets and on-disk profiles, then exit
```

`--max-age` accepts journalctl-style strings:

* relative durations: `"1 month"`, `"4 days ago"`, `"2 hours 30 minutes"`,
  `"36h"`, `"1d12h"`. The trailing `" ago"` is optional.
* absolute UTC datetimes: `"2025-02-21"`, `"2025-02-21 13:00:00"`,
  `"2025-02-21T13:00:00"`.
* `"never"`, `"off"`, or `"0"` disables the age check.

`--prune-profile` and `--prune-target` are repeatable and combinable:

```
cargo gc --prune-profile release \
         --prune-target model-viewer \
         --prune-target sound_lab
```

### What gets cleaned (and what doesn't)

The default sweep (no flags) does three things:

1. **Crate-name sweep.** Any `<profile>/.fingerprint/<crate>-<hash>/` whose
   crate is no longer in the project's `cargo metadata` graph is gone,
   along with its matching `deps/`, `build/`, `incremental/`, and top-level
   files.
2. **Per-unit age sweep.** Any fingerprint dir whose `invoked.timestamp` is
   older than `--max-age` (default `"1 month"`) is gone, along with its
   cascading artifacts. Pair this with a fresh `cargo build` immediately
   before running cargo-gc — the build touches every current unit's
   timestamp, so the only fingerprints that *stay* old are genuinely
   orphaned (e.g. an old feature-flag combo, or a bin you removed from
   `Cargo.toml`). Pass `--max-age never` to disable.
3. **Incremental session pruning.** Inside each surviving
   `<profile>/incremental/<crate>-<hash>/`, only the most recent rustc
   `s-*` session subdir is kept. Cargo never consults the older ones.

The default loop `(cargo build; cargo gc)` is still a fixed point: the
build refreshes every current unit's timestamp, the per-unit age sweep
finds nothing new to drop, and a second iteration is a no-op.

### Explicit pruning

`--prune-profile <NAME>` wipes `target/<NAME>/` entirely. Use it when
you've been testing one profile (say `release`) and don't need it any
more. NAME isn't validated against the project's known profiles — pass
anything you want gone.

`--prune-target <NAME>` wipes the artifacts (fingerprint, deps, build,
incremental, top-level bin/lib) belonging to a workspace bin/lib/example
target, in every profile dir. Shared dependency artifacts stay put — only
the target's *own* output is removed, so the next build of that target
just relinks instead of recompiling its world. Accepts either the
hyphen or snake form of the name.

### Real-world scale

Measured against a 53 GB target directory from a bevy/rapier-style
workspace (~500 transitive deps, several bin targets, ~50 fingerprint
dirs per workspace bin from accumulated feature-flag experiments):

| invocation                                  | reclaimed |
|---------------------------------------------|-----------|
| `cargo gc` (default `--max-age '1 month'`)  | 3.8 GB    |
| `cargo gc --max-age '1 hour'`               | 50.2 GB   |
| `cargo gc --max-age '2025-02-21 13:00:00'`  | 40.8 GB   |
| `cargo gc --prune-profile release`          | (whatever release was using) |
| `cargo gc --prune-target <some-bin>`        | (just that bin's footprint)  |

### Discovery

`cargo gc --list` (or `--list-targets` / `--list-profiles` individually)
prints what's available before you commit to pruning anything. Run from
this very repo:

```
$ cargo gc --list
workspace targets (4):
  bin      cargo-gc  (cargo-grime-cremator)
  bin      fixture  (cargo-gc-fixture)
  lib      cargo_grime_cremator  (cargo-grime-cremator)
  test     no_recompile  (cargo-grime-cremator)
on-disk profiles (1):
  debug
```

Target dir resolution order:
  1. `--target-dir` flag
  2. `$CARGO_TARGET_DIR` env var
  3. `[build] target-dir = "..."` from the nearest `.cargo/config.toml`
  4. `<manifest-dir>/target`

## Dual mandate (and one soft goal)

This tool exists to satisfy two non-negotiable rules:

1. **Clean.** Every file no longer needed for the next build must go.
2. **Never extend build times.** `(cargo build; cargo gc) × N` must
   compile only on the first iteration of the loop. From the second
   iteration onward, both commands are no-ops. Forever. Repeatable as a
   cron job, repeatable in CI, repeatable from a shell loop without ever
   "warming up" again.

These are non-negotiable. Mandate #2 is the one most other tools in this
space violate, and it's the one that turns "garbage collector" into
"hour-long compile penalty generator." If `cargo-gc` ever causes a
recompile that wouldn't have happened otherwise, that's a bug — please
file an issue.

Plus one **soft third goal**, intentionally subordinate to the two above:

3. **Match the from-scratch footprint.** After `cargo gc`, the target
   directory should be no bigger than `rm -rf target && cargo build`
   would produce. This is the *optimality target*. Everything `cargo gc`
   does beyond the strict crate-name sweep — the per-unit `--max-age`
   cutoff, `--prune-profile`, `--prune-target`, the rustc session
   pruning — exists in service of this goal, but never at the cost of
   the first two.

The default `--max-age '1 month'` is the most aggressive setting that
satisfies all three goals for most workflows: anything not built in a
month is almost certainly an orphaned configuration. If you want to be
more aggressive, tighten the value (and rebuild before you run gc). If
you want to be more conservative, loosen it or pass `--max-age never`.

## How it works

Cargo writes per-unit fingerprint metadata to
`target/<profile>/.fingerprint/<crate>-<HASH>/`. The 16-hex-char hash is the
same one cargo bakes into the artifact filename in `deps/`
(`lib<crate_snake>-<HASH>.rlib`) and the build dir
(`build/<crate>-<HASH>/`). So:

1. Run `cargo metadata --offline` to get the canonical set of crates and
   workspace targets the project currently knows about. This does *not*
   invoke the compiler — it just resolves `Cargo.lock` and reads manifests.
2. Walk every `<profile>/.fingerprint/` entry. If its crate name is in the
   live set, record its hash; if not, mark the fingerprint dir for deletion.
3. Sweep `<profile>/deps/` — any hashed file whose hash isn't live → gone.
4. Sweep `<profile>/build/` — any `<crate>-<HASH>/` dir whose hash isn't
   live → gone.
5. Sweep `<profile>/incremental/` — any dir whose crate prefix isn't live
   → gone. For surviving dirs, prune all but the most recent rustc session
   subdir (cargo only consults the newest one anyway).
6. Sweep top-level workspace bins/libs (`<profile>/<binname>`,
   `<profile>/lib<libname>.rlib`) that are no longer current targets.
7. Remove the marked stale fingerprint dirs last.

The sweep never touches `target/CACHEDIR.TAG`, `target/.rustc_info.json`,
`<profile>/.cargo-lock`, or anything it can't identify with confidence.

## Testing

Unit tests cover the parser, name matching, and target-dir resolution:

```sh
cargo test
```

Integration tests build a small fixture project with realistic deps
(serde, regex, tokio, rayon, …) into a tempdir, run the GC, and verify the
dual-mandate properties (zero recompile, zero re-removal). They're slow
because they invoke `cargo build`, so they're `#[ignore]`'d by default:

```sh
cargo test --test no_recompile -- --include-ignored --nocapture
```

## Comparison

| tool                  | algorithm                              | safe? | covers project target/ |
|-----------------------|----------------------------------------|-------|------------------------|
| `cargo-sweep`         | mtime + rustup toolchain               | risky | yes                    |
| `cargo-cache`         | global `~/.cargo` only                 | safe  | no                     |
| `cargo-prune`         | 2-hour timestamp clustering            | risky | partial                |
| `cargo-clean-all`     | recursive mtime                        | risky | yes                    |
| `cargo-grime-cremator`| fingerprint × Cargo.lock cross-ref     | safe  | yes                    |
| upstream cargo gc     | (per-project: still WIP)               | n/a   | not yet                |

## Limitations / out of scope

- No global cache cleaning (use `cargo-cache` for `~/.cargo`).
- No recursive multi-project mode (use `cargo-clean-all`).
- Absolute `--max-age` timestamps are interpreted as **UTC**, not local
  time. The tool deliberately doesn't drag in `chrono`/`jiff` or libc
  timezone code; if you want the local-time behavior, convert in your
  head or pass a relative duration like `"4 hours ago"`.
